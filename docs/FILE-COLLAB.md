# 文件协作与工作目录互斥

> 本文说明已实现的工作目录互斥、任务依赖和文件交接，并单独列出尚未实现的 Git 集成。行为契约见 [SPEC 4.12](../SPEC.md)，实现入口见 `internal/hub/core/`、`internal/node/service/` 与 `internal/node/inputs/`。

## 一、能力范围

| 层次 | 解决的问题 | 当前状态 |
|---|---|---|
| L1 工作目录互斥 | 防止受管任务同时修改同一工作目录 | 已有 hub 调度和 node 执行互斥 |
| L2 任务依赖与产物交接 | 等待上游结果，为下游准备可校验输入 | 已有依赖门控、同机复制与跨机取回 |
| L3 Git 集成 | 多个 agent 在隔离分支或 worktree 中修改并集成 | 规划，尚无可用配置或自动提交流程 |

文件交接独立于群聊；群聊仅可作为讨论或结果展示入口。SwarmMind 不提供多人实时编辑或任意目录同步。

## 二、L1：工作目录互斥

node 根据规范化工作目录计算 `workspace_id`，随能力卡上报，hub 按 `(node_id, workspace_id)` 决定任务是否可投递。实际路径与完整执行配置保留在 node。

互斥从已投递阶段计入，避免多个尚未开始的任务同时获得同一目录执行资格。node 还在输入准备与进程执行期间实施本地互斥；排队不计入 agent 的进程执行超时。hub 工作目录排队上限由 `WorkdirQueueWait` 定义，当前为 30 分钟，超时返回 `workdir_busy_timeout`。

路径标识依赖规范化结果。符号链接、大小写不敏感文件系统、bind mount 等别名需要结合 SPEC 的限制理解；不能仅凭路径散列保证识别任意底层共享存储。

互斥只覆盖 SwarmMind 受管任务。人工编辑器、其他脚本和共享 `config_home` 不自动受保护，不同路径也不必然表示没有共享资源。

## 三、L2：任务依赖

### 3.1 声明与准入

任务的 `depends_on` 引用上游任务的 **idem_key**，不是 task_id。提交时检查引用存在、非自引用、无重复与环、最大深度 4、可达上游数量最多 8；依赖关系参与提交指纹，提交后不能编辑。

`blocked_reason` 是等待原因字段，不是新的任务状态。等待任务仍是 `submitted`，占用信箱配额，最终仍可能因过期失败。上游失败、取消或结果不确定时，不应自动把下游当作可执行任务。

曾因上游失败而受阻的下游，在同一上游 idem_key 出现新的成功版本后可记录 `superseded_by`，但不会自动解除原阻塞。该字段是版本审计信息，不是独立的 `superseded` 协议状态；由人决定是否提交新的下游执行。

普通任务的同键重试不能用来重新执行已有任务。「上游新版本」涉及幂等记录生命周期等条件，不能理解为任意时候都可保留旧键修改内容重派。详见 SPEC 4.5/4.12。

### 3.2 输入准备

1. hub 放行依赖满足的任务后，node 在 `started` 与进程启动之前解析上游登记产物。
2. 同机优先从本机账本和源文件读取；需要远端数据时，经 hub 定位和中继到源 node。
3. 将文件复制到下游 `<workdir>/inputs/<上游task_id>/` 的准备区，核对登记大小和 SHA-256。
4. 校验通过后发布目录。采用复制而非硬链接，避免下游修改污染上游文件。
5. 准备失败返回 `input_prepare_failed`，不启动执行进程。上游已完成但没有登记文件可以是合法的纯答复结果，不因此伪造输入目录。

输入准备有独立超时预算；默认 60 秒。可重试的源节点离线或中继超时在预算内重试；无权限、材料不存在或完整性失败等情况明确返回错误，不跳过依赖继续执行。

### 3.3 文件安全与恢复

源文件通过 `inputs.OpenSourceFile` 打开，在原语层约束链接解析，并用已打开文件描述符检查对象类型。复制有字节上限并核对实际大小；目标路径定界，发布前重验路径组件。

每个上游目录单独原子发布，多上游整体不是一个文件系统原子操作。多步变更使用 journal 和目录同步，在崩溃后根据实际目录状态恢复。回滚失败保留恢复材料并报告具体位置，不能概括成「整个挂载始终完全原子」。

### 3.4 数据与保留边界

- 单文件最多 640 KiB，每个任务最多登记 8 个文件，还受完整帧限制。
- hub 保存任务结果中的产物引用，文件位于源 node；没有永久镜像或离线对象存储。
- 任务记录清理、文件删除和源节点离线是不同条件。记录仍在不保证文件仍可读取，文件仍在也不保证记录尚可寻址。
- 仓库修改不会自动登记为产物。需要交接代码时，应显式生成补丁或其他符合限制的文件。
- node 本机直执行入口不经过 hub 依赖门控，不支持把 hub 的依赖声明直接当成本机编排能力。

## 四、L3：Git 集成规划

早期方案提出了 `git_mode`、worktree/branch 隔离、自动提交、串行集成和清理流程。**这些不是当前可用的配置项或命令**，不应加入现有 node.yaml。

重新启动该项前，需先明确：基线提交如何固定；Git 写入与执行账本如何共同恢复；输出和输入如何排除出提交；冲突如何交给用户；凭证允许只读拉取还是允许推送；worktree 的删除如何避免提前丢失可取产物。

现阶段仍由用户或执行 agent 管理 Git 操作。文档不授权自动 commit、push、merge 或删除工作区。

## 五、验证要求

| 范围 | 核验事项 |
|---|---|
| 互斥 | 同目录串行、不同目录并发、排队超时、重启恢复和队首阻塞避免 |
| 依赖 | 非法引用、环、深度/级联上限、失败阻塞、版本审计、幂等冲突 |
| 输入 | 同机与跨机一致性、源离线重试、缺失分类、SHA/大小检查、无产物成功 |
| 文件安全 | 链接/特殊文件替换、路径逃逸、复制中增长、发布与回滚故障、journal 恢复 |
| 边界 | 所有准备失败均不启动 agent；普通任务无依赖时行为不变 |

具体可执行用例见 [TESTPLAN](TESTPLAN.md) 和跨机取回专项记录。测试范围与真实双机结论分别记录，不以设计要求代替已执行证据。

## 一、双方独立撞车的结论（实锤，直接采信）

1. **node 删除按钮无危险形态**：`.off-btn` 脱离 toggle 语境后无任何样式，node 的删除动作呈普通灰钮，hub 同类是红描边 danger。zcode、codex 在互不通气的情况下各自发现。
2. **危险确认形态漂移**：node 8 处 `window.confirm()` vs hub 全部 slim modal 确认。
3. **toast 双端两套运动机制**：hub `.show` 弹簧过渡，node `hidden` 硬切闪现。
4. **动效基建已完整，缺口在数据变化反馈**：召唤层 spring/out-quart、层世代状态机、D22 分区 diff 都在；轮询让数据在变，视觉完全静默。
5. **技术主线**：两端是整页 innerHTML 重建架构，微动效必须走「数据变化判据 + one-shot animation」，任何依赖同节点 transition 的方案在轮询路径上都会失效或重放。
6. **下拉菜单不自绘**：原生 select 的键盘/读屏体验免费且正确；chrome 精修（边框/focus/箭头/字号）+ 选后摘要常驻解决 90% 观感，只有选项多到难找才考虑可搜索 combobox。
7. **等宽数字**：zcode 的 `body{font-variant-numeric:tabular-nums}` 一行全局方案覆盖 codex 逐点清单的大部分，表格 td 已全局 tabular 证明口径成立；另补数量列右对齐与 `.artifact small` mono。

**C. V06 架构改造时机 → 定案：单独立项**
本分支只做纯视觉与反馈层，避免一次 PR 背两个量级的改动。

**D. 减法力度 → 定案：先走保守版**
保留 8 个导航；总览内容重做（前置待办→进行中→最近结果，删累计大数字与重复分布）；默认列表技术列（ID/提交方/重连次数/任期/SHA）收进详情或导出；登录剩余时间/回环地址/meta 文案降噪。激进版（8→3 导航）等 works/群聊使用数据说话后二阶段再定。

- 双端同组件截图对照（codex 最小样本：0/1/20/200+ 任务、长 ID、断网、中文组词、渠道启用/停用、通知表单两类）

## 五、不做清单（双方反提案合并，防跑偏）——技术层部分

1. 不自绘 dropdown/listbox（原生 select chrome 精修已够）
2. 不做导航滑块指示器（sliding pill 在重建架构里是常驻 JS 负担）
3. 不做骨架屏 shimmer（回环 API 亚秒级，「加载中」文字够）
4. 不做数字滚动 count-up / odometer（bump 已是动效上限）
5. 不做表格行 FLIP 重排动画
6. 不做 details 展开高度动画
7. 不做路由 View Transitions
8. 不新增任何 hover lift 面（群卡 lift 是钦定全站唯一）
9. 语义色不扩编，FINAL 金色不成先例
10. 不做成功庆祝动效（任务完成是常态不是里程碑）
11. 玻璃不扩编（topbar/toast 两个真重叠位置的技术依据在案）
12. 深色模式单独立项
13. 不用缩小字体解决密度（地板 12.5px）
14. 不强求双端每页相同（SPEC 能力白名单，不造假对称）
15. 不拿动效遮白闪（白闪的解是局部更新，不是渐变闪）
16. 不把错误全塞 toast、不反复弹确认（可逆动作不加确认层）

## 六、产品层裁决（第二维度：这个产品好不好）

> 来源：codex 产品评审 63 条 + 生产数据实证 + Hana 产品分析。判断标准只有一条：信息能否帮助用户派任务、观察进展、审异常、收结果。

### 6.0 产品结论

界面围绕协议而不是围绕工作：用户看到很多「数」和「状态」，缺一条稳定答案——**哪件工作需要我做什么，处理后是否真的结束**。核心循环四步里，「审异常」与「收结果」的闭环存在断路；先修闭环，再谈减法，最后才是视觉打磨。

### 6.1 闭环断路（产品层 P0，优先于一切视觉条目）

| # | 断路 | 证据 | 修法 |
|---|---|---|---|
| P0-1 | **核对完待办不减**：人工核对只写 Review 记录，不改 needs_review，待办永远挂着 | internal/hub/core/review.go:23-41 | 待办口径改为「needs_review 且无 review」；已核对进历史详情；协议状态原样保留 |
| P0-2 | **取消承诺过强**：双端显示「执行进程已整组终止」，实际是尽力取消、离线补发，无确认依据 | hub/core/cancel.go:13-28；H/app.js:1889 | 无确认时改说「已登记取消，执行机停止情况待确认」——用户可能据此立刻操作同一工作目录 |
| P0-3 | **告警通道失效不告警**：通知渠道投递失败只进日志，无投递状态展示 | internal/notify/dispatch.go:169-187 | 渠道卡加最近成功/最近失败与原因摘要，失败前置修复入口 |
| P0-4 | **站内通知易失**：内存保存、容量上限、重启清空（index.html title 自认「重启后清空」） | internal/notify/inbox.go:3-21 | 待处理事项从持久任务/工作单事实重建，不依赖铃铛未读；无外部渠道时明示「关闭页面后收不到异常」 |
| P0-5 | **伪并发读数**：机器卡「进行中 n/8」实为投递窗口（offered+acknowledged），不是执行并发 | hub/core/view.go:24 | 删除伪读数，投递窗口进诊断详情 |
| P0-6 | **同一事实两个承诺**：总览说离线任务会暂存，派发页离线目标禁选且不暂存 | H:1202 vs H:2131-2137 | 每个入口只说自己的事实：「本页离线不能派发；支持暂存入口提交的重连后送达」 |
| P0-7 | **权限展示过强**：permission_mode 原始标签像隔离承诺，SPEC 自认白名单不构成隔离；停止开放不停在途工作 | N:981、1154；SPEC.md:264 | 权限可理解化+「不确定」兜底；开关语义改「停止接受外部新任务」，停现有任务走独立动作 |

注：P0-1/3/4/7 涉及后端口径或新查询能力，按 SPEC 六.六契约同步 MCP 与实测，不以「只做前端」绕过。

### 6.2 减法裁决（裁决点 D，伦哥拍板）

**生产数据实证**（2026-10-28 查 hub_state.db）：nodes 2、tasks 9、batches 50/47——真实使用中。**works 0 行**：拆解工作单无自动清理（独立生命周期），10-27 刚上线尚无真实使用——不是僵尸功能，砍导航为时过早。

| 力度 | 内容 | Hana 倾向 |
|---|---|---|
| 保守版 | 保留 8 个导航；总览内容重做（前置待办→进行中→最近结果，删累计大数字与重复分布）；默认列表技术列（ID/提交方/重连次数/任期/SHA）收进详情或导出；登录剩余时间/回环地址/meta 文案降噪 | **先走这版** |
| 激进版（codex 极限） | hub 8→3（任务/机器/设置，任务即首页含派单与异常）；node 删总览；工作单从任务进入；群聊降为按需工具入口 | 二阶段：等 works 与群聊使用数据说话再定 |

无争议减法（不属裁决，直接进批次）：工作单列表前置目标/阻断/下一步，尝试数/任期/关闭时间进详情【H18】；装机向导前置「尚未登记/等待连接/已连接」状态【H07】；派单表单收成「交给谁、做什么、什么权限」，参数折叠为高级输入【H08】；产物前置文件名/易读大小/取回动作，SHA 进详情【H15】；任务详情五段化（做什么→当前事实与下一步→结果与可取文件→异常核查→折叠证据）【H13/X05】。

### 6.3 回访与留存（工具产品的留存 = 效率与信任）

- 回来的理由应是「昨天交代的工作有可收取结果，没完成的有明确原因」，不需要检查服务有没有悄悄死【codex 五】
- 工作层待决（工作单 blocked/待收集、群预算耗尽/待定版）目前只在各自页面显示，汇入既有通知渠道，只对受影响工作发【R03】
- 通知文案前置工作摘要与回到工作的入口，不带编号让用户全站搜索【R04】
- 已完成任务随保留期清理：「已归档」用语纠正为「已删除」，删除「暗示仍可恢复」的错误承诺【R05】

### 6.4 信任三问

1. **agent 在干嘛？** 能看执行记录，不能持续看真实进度。诚实说明观测边界（「当前只知道进程执行中」）比转动的「运行中」徽标更可信，不伪造百分比【T01】
2. **会不会闯祸？** 有配置边界但展示成更强保证。修事实表达与控制闭环，不引入审批中心/安全评分【T02/T03】
3. **出事能不能发现？** 终态可发现，但告警失效、过程阻断、监测链路断开是盲区。四个最低限度事实前置：数据是否过期 / 有无未处理异常 / 关页能否通知 / 取消是否确认【T04】

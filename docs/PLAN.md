# SwarmMind 项目方案与实施计划

> 本文维护项目定位、技术取舍和阶段验收要求。协议与接口契约见 [SPEC](../SPEC.md)，组件与数据流见 [架构详解](ARCHITECTURE.md)。
> 状态基准：2026-10-26，开发分支已包含 P5 Work W1–W3 和 P5.1 D1 实现。代码实现、版本测试、分支合并与生产部署分别记录。

## 一、项目定位

SwarmMind 是面向个人自托管场景的跨机器 agent 任务调度与结果管理系统。用户将已有 CLI 工具或 agent 配置为节点能力，通过 Web、CLI、MCP 或 REST 提交任务，并查看执行状态、最终答复和输出文件。

典型场景包括跨机器构建、代码分析、系统巡检和文件处理。系统负责节点连接、可靠投递、执行记录与产物交接；任务拆解可由用户完成，也可委托给指定的 Prime agent。

当前设计按个人管理多台机器的信任模型组织，不包含多组织租户隔离、公开 agent 市场或任意外部服务的统一授权。

## 二、组成与部署条件

| 组成 | 职责 | 部署条件 |
|---|---|---|
| Hub | HTTP 管理服务、节点会话、能力目录、任务账本、离线信箱与中继 | 节点能够访问其接入地址；可以部署在公网、内网或仅用于回环测试 |
| Node | 注册本机能力、保存执行账本、启动本机进程、准备输入与读取产物 | 能主动连接 hub；不需要向公网开放本机 API |
| CLI | 人工提交与查询任务 | 可访问 hub 管理面 |
| MCP | 将 stdio 工具调用适配到 hub 或 node API | 由 MCP 客户端启动，并配置相应地址和凭据 |

hub 是网络服务端和控制面，但不直接启动用户任务进程。若中心端所在机器也要执行任务，应在该机器另行运行 node。

节点接入默认使用 WSS；管理面单独监听，远程访问需要配置 HTTPS 反代或 SSH 转发。只有节点接入链路共享一个 WSS 端口，整个系统并非只有一个监听端口。

## 三、主要技术决策

| 决策 | 方案 | 原因与限制 |
|---|---|---|
| 实现语言 | Go，分别构建 hub、node、CLI、MCP | 核心运行时不依赖外部数据库或消息队列；agent 及其环境另行安装 |
| 连接模型 | node 主动建立到 hub 的 WSS 长连接 | 适用于没有公网入站地址的节点；当前消息与产物读取经 hub 中继 |
| 投递方式 | 异步提交、持久化确认、重传和幂等去重 | 提交返回 task_id；接受、执行和结果确认分别记录，避免将响应丢失视为未执行 |
| 状态存储 | hub 事务快照与 node 执行账本 | 支持进程崩溃恢复；完整磁盘掉电耐久性不能仅由原子 rename 推导 |
| 执行授权 | node 固定命令、目录和参数基线，逐项授权任务参数与环境覆盖 | 不替代操作系统账户权限或 agent 自身沙箱 |
| 接入方式 | 本机 CLI 执行配置，外部调用经 MCP/REST | 能执行 CLI 不代表可复用任意 IDE 原有会话；会话联动需专门适配 |
| A2A | 当前实现对齐 v0.2.6 的兼容子集 | 不使用 a2a-go；仅支持的端点和偏差见 SPEC，不能宣称完整兼容 v1.0 |
| 文件交接 | 登记输出文件、校验 SHA-256、复制到下游输入区 | 受大小、数量、源节点可达性与任务记录保留期限制，不提供永久对象存储 |
| 编排 | Prime 作为普通 API/MCP 调用者，Work 保存多步执行事实 | 不在 hub 内加入自动选主或自主重派服务 |
| 派发建议 | hub 内嵌 DecisionProvider，D1 使用 llm-as-jev | 建议可覆盖，不作为提交前置；模型概率未证明统计校准 |

依赖白名单以 SPEC 第三节和 go.mod 为准。组网方案采用中心注册与中继模式。

## 四、可靠性与安全边界

- hub 持久化任务后才确认提交；node 持久化接受记录后才确认投递；hub 持久化结果后才确认结果回传。
- 普通任务同键同内容的提交重试返回原任务，同键异内容返回冲突。重复投递由同一 node 账本去重。
- node 重启时，已接受但未开始的任务可以继续调度；已开始但未记录完成的任务进入 `needs_review`，需要人工核对，不自动重新执行。
- 会话 epoch 隔离旧连接，任务租约校验隔离过期派发结果。租约缺省兼容和混合版本限制见 SPEC 4.11。
- hub 管理者、持有有效 PAT 的客户端与已接入节点均处于系统信任边界内。当前不提供按业务资源细分的多租户权限体系。
- hub 可以读取经其路由的任务内容和结果。当前 WSS 是传输加密，不是端到端加密。
- 同工作目录互斥只约束 SwarmMind 管理的任务；外部编辑器、脚本和其他进程不会自动参与互斥。

容量和保留期统一引用 [运维文档](OPERATIONS.md)，不在多份规划中维护不同的数值副本。

P0–P5 是项目内部实施阶段，不等同于软件发布版本。以下列出阶段目标，是否通过验收以对应报告为准。

| P1 基础实现 | hub/node/CLI、可靠投递、执行账本、回环演示 | SPEC DoD 1–10 |
| P1.5 工作目录互斥 | 同目录串行、不同目录可并发、排队超时与重启恢复 | FILE-COLLAB L1 用例 |

| P3 用户与接口入口 | 双端控制台、登录/PAT、MCP、A2A 兼容子集 | 接口、权限、交互与互操作测试 |
| P4 日常运行 | Windows 服务、终态通知、依赖与跨机产物挂载、任务列表 | 工程验收及真实使用观察期 |

## 六、暂缓能力

| 能力 | 重新评估条件 |
|---|---|
| 群聊完整协议：发言许可、node 推送、多维预算 | 出现现有 REST/MCP 消息协作不能满足的实际场景 |
| Jev 本地 provider 与级联策略 | 按 D3 明确部署资源、对照数据与校准评估 |
| A2A 完整协议升级 | 有明确协议版本和功能要求的调用方 |
| P2P 直连、大文件传输 | 中继成本或当前文件限制成为实际瓶颈 |
| 端到端加密 | 明确 hub 不可信的威胁模型和密钥管理方案 |
| Git 自动集成 | 实际多 agent 同仓库协作需求，并具备凭证、冲突与保留策略 |
| IDE 会话联动 | 确定目标客户端、会话边界与适配接口 |

暂缓表示没有纳入当前交付承诺，不代表已有实现，也不预设必定在哪个发布版本提供。

## 七、开发与验收流程

1. 在开发前确定 SPEC/交互契约、范围和可执行测试用例。
2. 面向管理面的 REST 能力按 SPEC 六.六同步交付 MCP；人工专属端点按显式豁免清单处理。
3. Web 交互变更先完成原型评审，再实现；共享展示机制按双端一致性契约验证。
4. 完成构建、测试和独立会话验收，修复失败项后复验。
5. 报告区分本机测试、真实双机、Windows 真机和生产观察，不相互替代。
6. 合并、提交与部署遵循仓库授权规则；测试通过本身不构成发布授权。

工程条件为 SPEC DoD 和测试循环通过；P4 产品条件另要求连续 14 天真实使用观察，起算、最低任务量和中断规则须先批准。详见观察期方案。

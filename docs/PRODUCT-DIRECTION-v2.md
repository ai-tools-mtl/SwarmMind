## 一句话重定位

**SwarmMind 是伦哥自己的跨机器派单工作台：在任何一台机器上说清目标，系统告诉你活在哪台机器上干、干完了没有、结果在哪；网络断了任务在离线暂存区等着，执行中断拿不准的结果会标记出来等你确认。**

不是：多组织协作平台、agent 生态市场、协议标准化的旗舰。
是：一个人、几台机器、把活派出去放心干等结果。

用户只有一个，验收标准只有一条：**伦哥的日常动线零断点**——说目标 → 派出去 → 干别的 → 收到通知 → 取结果；出例外时系统主动找他。

## 为什么现在的方案不合理

三方审查的三个共识发现：

1. **第一天走不通。** README 快速开始有 6 处照抄必挂的断点（二进制名对不上、hub.yaml 三个无效字段、node.yaml 键名错误、agent 示例过不了校验、curl 派单必吃 401、MCP 跨机默认不可达）。文档停留在 P3 之前，代码演进了多轮没人回头重写。现成的 `scripts/demo-loopback.sh`（跑通全链的现成道具，参考耗时约 1 分钟，含构建与故障演练）被埋没，装机向导零提及。

2. **概念膨胀比约 5:1。** 用户心智需要的最小概念约 8 个（机器、任务、结果、产物、核对、令牌、权限、机器在线状态），文档/接口实际暴露约 40 个（同义词合并后的保守计数，非可复现统计）。epoch、租约、信箱、superseded、host_term、DecisionProvider……大部分是「写给自己看的备忘录」语气。

3. **功能优先级与真实场景错配。** 唯一用户的真实动线是「MCP 派单 → 等结果」，而 Roadmap 的 P4 收尾里一半是群聊自治的高级功能（发言许可制、推送扇出、多维预算）——单人群聊用不上。真正影响日常的 Windows 服务化（伦哥的真实 Windows 节点靠 schtasks 硬撑）反而排在清单中间。

## 名词人话化（核心整改）

原则：**用户界面和文档里，人话在前，术语可选；用户不该学的概念藏进实现。**

### 替换边界（先划清）

- **替换**：界面显示文案、文档说明性文字、控制台页签与状态名
- **原样保留（机器契约）**：代码标识符（`prime_agent`/`prime_token`）、API 路径（`/api/v1/prime`）、MCP 工具名（`swarmmind_*`）、配置键名、环境变量；文档保留术语对照表与历史审查记录，防新旧失联

### 关键术语翻译表

| 现名 | 人话 | 处理 |
|---|---|---|
| 统筹载体 / Prime | **智行管家**（已决） | 界面与文档换人话；机器契约保留。需说明：它是某个 agent 扮演的**角色**（非新增常驻服务），且区分「本机管家的权限」与「全网管家的权限」 |
| StartLux / DecisionProvider | （藏）「派给谁」的自动建议 | 从必经链路移除，降为实验；界面显示「建议派给 X（本地规则/云端模型）」——**不显示百分比置信度**（规则降级路径固定 0.5，显示百分比会被误读为校准过的成功概率），改为显示决策来源与降级状态 |
| needs_review / 待人工核对 | **等你确认** | 界面主文案「这个任务结果拿不准，等你确认」；「待人工核对」可留作次级 |

| 信箱 mailbox | **离线暂存** | 界面说「机器不在线，任务先存着，上线就送」 |
| enroll / 接入 | **添加机器** | 向导文案统一「添加一台新机器」 |

| swarmmind_* 工具名 | 保留（给 agent 看的，语义已直白） | 工具 Description 用人话重写 |

### 概念分级（codex 审计采纳）

- **默认隐藏（诊断可查）**：epoch、租约、fencing、三段 Ack、账本恢复态、seq 游标、幂等键、trace
- **调用层自动管**：幂等重派、依赖寻址、产物校验——不含 needs_review 任务的自动重跑（那是立身哲学，永不自动）
- **首次用到时一句话解释**：令牌、开放开关、保留期、并发上限
- **必须清晰浮出**：活在哪台机器、排队原因、结果是否完整、是否等你确认、执行权限

## 新阶段规划（批准后取代 PLAN 第七章 P4/P5）

### P4（重定义）：一个人每天用得顺

顺序即优先级（工期均为待拆解估算）：

1. **README 重写 + 黑话清扫**（估 1-2 人日，含双端界面文案同步）——最短修复路径，每一台新机器、每一次演示都受益
2. **Windows 服务化**——真实拓扑的无人值守短板，schtasks 是权宜不是终态；P4 第一项功能开发（在文档修复之后）
3. **任务终态 IM 通知**（估 1-2 人日，待设计）——飞书/Telegram webhook 出站；解决「派完活切走干别的，好了自动来消息」。边界声明：通知失败不改变任务终态，重试/去重/验收待设计；通知≠手机上能看详情，状态页与产物取回仍是独立能力
4. **产物挂载与跨机取回**（L2 第二子批既有项）——智行管家的复合任务目前最后一段纯手工环节；与群聊解耦（文件交接是执行基础能力，群聊只是可能的展示入口）。注意产物受容量、源节点在线、保留期（结果确认后 24h）约束
5. **`swarmmind_tasks` 列表工具**（新增，补 MCP 工具面缺口）——REST 已有列表端点，MCP 没透出；「我现在跑着什么活」是高频查询

验收：两层。工程层沿用 SPEC DoD 十一条与独立会话测试循环（双机断线/权限拒绝两项待归档的事实不因本文档改变）；产品层为「14 天真实使用观察期」——观察期在工程验收全绿之后开始，最低任务量、阻塞判定标准、中断后是否重新计时，开工前另行定义。

### P5（重定义）：复杂工作可恢复

- 执行事实与接管：整件工作（多步骤）的记录、输入、产物、验收结果——Prime 崩溃后任务继续但无人收集，是实际缺口
- 多步骤任务的断点查看：调度 agent 消失后，能看见哪些完成/执行中/未开始，不用猜不用盲目重派
- Git 集成（L3）**推迟**：等第一次真实撞上「两个 agent 改同一个仓库」再启动

### 实验区（有真实需求才晋级）

群聊完整协议（发言许可/推送扇出/多维预算/消息过期）、StartLux 决策产品线、A2A 生态深化、P2P 直连、端到端加密、IDE adapter。

**冻结理由**：群聊在单人群场景下现有子集够用（任务关联与历史保留，暂停为 RFC 完备性扩状态空间）；StartLux 从必经链路移除（显式指定+简单规则已够，任务结果与候选能力数据保留，未来可恢复）；A2A 停止新增承诺（现状三份文档版本号各说各话：v1.0 / v0.2.x / v0.2.6，先统一口径为「A2A 兼容端点，对齐 spec v0.2.6 兼容子集，完整协议兼容与 v1.0 对齐推迟到实验区有真实调用方再议」）；端到端加密当前暂不投入（自己的 hub 也可能承载敏感任务与凭据，若未来成为真实威胁场景再议——不排除需求，只是排序）。

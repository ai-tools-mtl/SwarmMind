# SwarmMind 产品方向 v2

> 方向决策日期：2026-10-24。本文整理既有定位、优先级与命名决策，不代表列出的规划全部交付。
> 2026-10-26 的增量状态：Work 已有 W1–W3 实现；分配建议按 P5.1 D1 重新纳入当前范围。实施状态见 [项目计划](PLAN.md)，行为契约见 [SPEC](../SPEC.md)。
> 2026-10-29 目标澄清：以[远程原生 agent 与持久会话协作](VISION-persistent-agent-collaboration.md)补充核心场景与下一阶段优先级。下列 P4/P5 是既有工程阶段，不代表持久会话目标已经完成。

## 一、目标用户与工作流程

SwarmMind 面向由一名用户管理多台机器和多个 agent 的自托管场景。核心目标是远程使用已有原生 agent 的模型与工具环境，在各自的持久线程中开展多轮协作。典型目标流程为：用户给需求 → Prime 梳理 → zcode 原线程编写 → Codex 原线程审查 → 反馈回原编写线程 → 通过后交付，或触发停止规则后请用户裁决。

当前已实现的基础流程仍为：确定目标与执行者 → 提交任务 → 查看进度或等待通知 → 获取结果与产物 → 处理执行异常。Work 的执行事实恢复不能替代原生对话恢复。

产品应让用户能明确回答以下问题：

- 任务由哪台机器、哪个 agent 执行？
- 任务已被接受、正在等待还是已经结束？
- 等待的原因是什么，用户是否需要操作？
- 结果和产物是否完整，可以从哪里获取？
- 任务中断后哪些事实已确定，哪些仍需人工核对？

多组织权限、agent 市场和通用工作流平台不属于当前产品范围。

## 二、改进依据

早期文档与界面存在三个问题：配置示例随实现变化而失效；用户操作说明混入过多内部协议细节；规划功能与已交付能力缺少清晰区分。

改进应以完成实际任务为标准，而不以新增术语或功能数量为标准。快速开始必须能在隔离环境中复现，异常说明必须给出原因与可执行的下一步，规划必须标明状态和验收条件。历史发现的具体问题由对应测试与修订记录保存，不作为当前缺陷继续陈述。

## 三、术语和说明方式

用户文档使用准确、直接的中文。技术术语在首次出现时解释；需要配置、调用接口或排查问题时提供原始标识符。避免口号、拟人化保证和没有条件的「自动完成」「绝不失败」等表述。

| 标识符 / 概念 | 用户侧说明 | 保留的信息 |
|---|---|---|
| Prime | 编排 agent；界面显示名为「智行管家」 | 是现有 agent 的角色；本机与全网入口权限不同 |
| `needs_review` | 待人工核对；当前界面显示「等你确认」 | 结果不确定，不代表未执行，不自动重新执行 |
| mailbox | 离线任务暂存 | 受配额与过期时间限制，重连后满足条件才投递 |
| `exposed` | 是否允许经网络调用该能力 | 由节点主人配置，不能与停止在途任务混淆 |
| epoch / fencing | 会话代次 / 执行租约校验 | 主要出现在诊断与开发文档，不影响标识符原值 |
| `superseded` | 上游版本变化导致当前任务失效 | 指出关联版本和后续操作，不仅显示内部错误码 |
| StartLux / `swarmmind_decide` | 可选的执行者分配建议 | 标明决策来源与降级状态；数值置信度不当作成功概率 |

API 路径、配置键、工具名和环境变量不因展示名称而重命名。文档引用现有界面文字时可以保留原文，但应同时准确解释行为。

## 四、信息分层

| 场景 | 应提供的信息 |
|---|---|
| 首次使用 | 组件职责、环境要求、有效示例、验证结果、停止与清理方式 |
| 日常任务管理 | 执行者、状态、等待原因、输出与操作入口 |
| 异常处理 | 原因、影响、是否可能产生副作用、查询或人工核对方法 |
| 接口调用 | 完整参数、凭据种类、返回语义、幂等与错误行为 |
| 运维诊断 | 时间、代次、租约、日志、容量、持久化和恢复边界 |

同一项机制不必在所有页面展开，但不能为简化说明而隐藏影响用户决定的限制。例如，产物存在容量和源节点在线要求，任务重试存在副作用与幂等约束。

## 五、阶段优先级

### 下一阶段主线：先验证原生续聊，再建设协作循环

先验证用户实际版本的 Codex/zcode 原生线程创建与恢复能力，再建设 Session/Turn 与 REST/MCP，随后实现固定线程上的编写—审查循环和双端日常入口。验收必须覆盖真实远端两轮续聊、多线程隔离、版本绑定、断线恢复与预算停机；详见[方案与 S-01–S-10](VISION-persistent-agent-collaboration.md)。本项为待实现目标，工程编号与接口需另行落入实施 RFC；不因已有群聊、Work 或无头 CLI 调用而标为完成。

### P4：完善日常运行

| 优先项 | 目标 | 当前状态说明 |
|---|---|---|
| 文档与界面说明 | 首次安装、提交、异常恢复有可验证步骤 | 持续维护；文档修订不自动改变运行界面 |
| Windows 服务 | 支持自动启动、故障恢复和日志管理 | 仓库已有实现；真机验收另行记录 |
| 终态通知 | 任务结束后通过已配置渠道通知用户 | 仓库已有通知渠道；失败不改变任务终态 |
| 文件交接 | 下游自动准备同机或跨机上游产物 | 仓库已有依赖与挂载实现，受文件与源节点限制 |
| MCP 任务列表 | 查询全网任务并筛选 | hub 模式已有 `swarmmind_tasks` |

工程验收按 SPEC DoD 与独立测试循环执行；真实使用观察另外按 [观察期方案](archive/OBSERVATION-P4-plan.md)执行。没有报告时不标记已完成观察。

### P5：多步骤工作恢复

Work 保存目标、步骤、执行尝试与事件，使新任期能读取已有事实后继续编排。接管不应新增未经确认的执行尝试，也不应把不确定结果自动视作失败后重跑。

W1–W3 的创建、查询、绑定派发、接管、收集和管理台已在开发分支实现；W4 有历史双机报告，具体采证范围及其缺口按 [报告](archive/TESTREPORT-w4-p5.md)记录。当前代码与报告版本需分别核对，详见 [Work RFC](archive/RFC-work-resume.md)。

### P5.1：可选的执行者分配建议

D1 已加入 hub 决策服务、REST/MCP 查询和管理台建议区。当前采用 llm-as-jev 的 Choice 输出形式；并非已部署 Jev 原生或本地模型，也不承诺返回概率已经校准。真实模型终版逐场景复验待补；D2 群聊联动和 D3 本地 provider/级联为后续范围。

### 暂缓范围

群聊发言许可与推送协议、多维预算、A2A 完整协议升级、P2P、端到端加密、IDE adapter 和 Git 自动集成按实际需求重新评估。决策服务以当前 P5.1 分批范围为准，不再笼统标为全部冻结。群消息现有的滚动裁剪与 24 小时过期机制不属于未实现项，具体范围见 [群聊设计](GROUP-RFC.md)。

## 六、已确定的决策

1. 当前主要场景为个人管理多台机器。
2. Prime 保留现有界面显示名「智行管家」，机器契约不变。
3. 保留群聊现有能力，扩展协议按需求另行立项。
4. P4 验收包含工程验证和真实使用观察，不以其中一项代替另一项。
5. A2A 只声明当前 v0.2.6 兼容子集，具体支持和偏差以 SPEC 为准。

# SwarmMind 产品评审：让管理台围绕工作，而不是围绕协议

日期：2026-10-28。范围：hub 与 node 全部现有页面、任务/工作单抽屉、建群/装机/通知配置流程，以及与判断有关的取消、核对、通知实现。

本轮为源码只读评审，仅新建本报告。未修改仓库及既有临时文件，未运行 git、构建、测试、服务或真实任务，未作浏览器实测。文件行号相对仓库根目录；H＝internal/hub/web/app.js，N＝internal/node/web/app.js。结论描述的是当前源码可见行为，未来验收条目不代表已经通过。参考了 docs/FE-POLISH-PROP-zcode.md 与 docs/FE-POLISH-PROP-codex.md；不复述其视觉、动效、键盘或布局建议，少数共同问题仅讨论决策后果。

判断标准只有一个：信息能否帮助用户派任务、观察进展、审异常、收结果。分级：必须修＝错误承诺、错误行动指引或核心循环断路；建议修＝减少判断成本；可不修＝可以保留且本轮不值得投入。四类信息的“噪音”指默认位置缺乏决策价值，不等于底层数据应该删除。

## 一、产品结论与先后顺序

当前管理台已经能表达执行结果、人工核对与恢复边界，但仍把内部协议当成用户的工作对象。用户看到很多“数”和“状态”，却缺少一条稳定答案：哪件工作需要我做什么，处理后是否真的结束。

先修六项：取消不等于已经停止；核对完必须退出待办；本机任务必须有真实可达的异常处置路径；通知失效必须可见；本机自治不能显示成故障；装机引导不能把可选管家当必需。随后删除重复总览与技术列。不要先增加新仪表盘、欢迎页、成功率曲线或聊天活跃度。

下面的信息盘点兼作逐项处置单；同一条中以“；”连接的是共享位置、共享决策用途的一组字段，独立处置的字段另列。

## 二、逐页信息价值盘点

### A. 双端壳、登录与首屏

**A01｜建议修**
【现状】hub 顶栏会话剩余时间、总览再次显示登录剩余时间及访问地址（H:954、1193-1195）；node 顶栏显示“Bearer 令牌已就绪”、固定回环地址说明（N:741；internal/node/web/index.html:15）。 /【判断】噪音 /【建议】删除日常重复展示，地址与鉴权方式进详情，临近过期时前置续登提醒。 /【理由】用户需要避免工作中断，不需要一直监看登录实现。

**A02｜必须修**
【现状】hub 总览“中心端状态”固定在线（H:1191）；node 读取失败在下一轮静默重试（N:638-645），hub 全部资源从未成功时隐藏新鲜度（H:815）。 /【判断】健康感知 /【建议】前置“数据是否可信”的状态，仅在当前读取成功时表示已连接，失败时明确上次成功时间或尚未加载。 /【理由】旧页面还能打开不能证明后台正在正常接单，假健康会让用户放心离开。

**A03｜可不修**
【现状】hub 支持密码、首次初始化与管理令牌恢复，node 明示本机令牌获取位置和本地存储范围（H:1069；N:757-762）；两端页脚有版本（H:983；N:732）。 /【判断】审计回溯 /【建议】折叠恢复通道和版本到帮助/诊断，保留令牌首次获取说明。 /【理由】换机器时能找回入口有真实价值，平时不必突出技术身份。

### B. hub 总览

**H01｜建议修**
【现状】四格显示全网任务、执行中、已完成、等你确认，下方再显示全状态分布与最近五条任务（H:1184-1208）。 /【判断】执行中和未处理异常为决策必需；全量/完成总数与重复分布为噪音 /【建议】删除重复全状态模块及累计式大数字，前置“待处理异常 → 进行中工作 → 最近结果”，复用现有列表。 /【理由】用户回来是接着做事，保留窗口内有多少记录不会改变下一步。

**H02｜必须修**
【现状】总览及导航的“等你确认”按 status 全数计入（H:1174、972），而核对只写 Review、不改变 needs_review（internal/hub/core/review.go:23-41；H:1945）。 /【判断】决策必需 /【建议】前置未核对集合（needs_review 且无 review），已核对进历史详情，协议状态原样保留。 /【理由】做完一件事却不能让待办减少，会使用户放弃相信待办。

**H03｜建议修**
【现状】“需要你关注”在无 needs_review 时称“当前没有待办”，失败任务仅附计数，离线机器无论是否影响工作一律告警（H:1199-1202）。 /【判断】健康感知 /【建议】前置仍有工作受影响的失败/离线/取消待确认项；无工作受影响的离线仅进机器详情；没有失败处置记录时用“失败待查看”，不要声称已处理。 /【理由】长期离线备用机不该与正在阻塞交付的机器争夺注意力。

**H04｜建议修**
【现状】总览标题显示在线机器/全机器与网内能力项数，中心状态卡又重复能力数；唯一突出动作是添加机器，空任务引导去 API 提交（H:1183、1195、1208）。 /【判断】可派目标是决策必需；裸能力总数为健康感知 /【建议】前置“派任务”，无可用执行者时才前置添加机器/开放能力，能力总数进机器页。 /【理由】系统已有派单表单，不该让第一次使用的人先学 API 或继续装机。

### C. hub 机器页与添加机器向导

**H05｜建议修**
【现状】机器表有机器名、连接状态、重连次数、进行中任务、开放能力名/描述、撤下说明（H:1215-1225）。 /【判断】名称、连接与能力为决策必需；epoch 为噪音；撤下说明为审计回溯 /【建议】前置名称、能做什么、是否可派；重连次数进日志；撤下说明进详情。 /【理由】选择执行者需要知道能否做事，连接代次不能代替可用性。

**H06｜必须修**
【现状】“进行中任务”显示 n.inflight / 8 并声称最多同时进行八个任务（H:1218、1225），实际 Inflight 仅统计 offered+acknowledged 投递窗口（internal/hub/core/view.go:24；internal/hub/core/dispatch.go:130-133）。 /【判断】健康感知 /【建议】删除伪并发读数；实际执行/等待数有真实数据再前置，投递窗口进诊断详情。 /【理由】传输窗口不是执行并发，错误负载信息会误导派单。

**H07｜建议修**
【现状】装机向导依次机器 ID、一次性令牌、手贴 hub.yaml 并重启、部署包/Docker/手动配置、等待上线（H:1294-1298、1333-1354、1396-1438、1562-1563）。 /【判断】连接目标与完成状态为决策必需；令牌/配置片段为审计回溯 /【建议】前置“尚未登记/等待连接/已连接”，保留推荐安装路径；备用安装方法和 YAML 进详情，一次性凭据仅在确需交接时展示。 /【理由】生成了令牌或下载了安装包不代表机器已经加入，应让人清楚卡在哪一步。

### D. hub 派发与提交回执

**H08｜建议修**
【现状】派单有机器、智能体、摘要与权限模式、任务描述、可选命令行参数、参数建议、自动恢复密钥和三条运行规则（H:2086-2111、2186-2199、2021-2030）。 /【判断】目标/描述/权限为决策必需；参数为专家决策信息；密钥及协议说明为噪音 /【建议】前置“交给谁、做什么、以什么权限执行”，参数折叠为高级输入，恢复密钥进详情，运行规则折叠。 /【理由】普通派单只应要求用户提供工作意图，CLI 专家仍可按需传参。

**H09｜建议修**
【现状】未决提交提供“同键重试/放弃等待”，成功跳到含 batch_id、汇总与各任务去向的批次报告，主按钮是“再运行一次”（H:2104、2293-2304）。 /【判断】提交是否成功及任务去向为决策必需；单目标批次 ID 为噪音 /【建议】单目标时删除中间批次展示，前置“查看此任务”；未决状态保留安全重试并改成“确认上次提交”，技术键进详情。 /【理由】用户完成的是派一件工作，不应再辨认提交批次与执行完成的差别；重试安全机制必须保留。

**H10｜必须修**
【现状】总览离线告警说任务会暂存（H:1202），派发页却明确离线目标禁选且提交端点跳过、不暂存（H:2093、2131-2137）。 /【判断】决策必需 /【建议】前置当前入口的事实：“本页离线不能派发；已由支持暂存的入口提交的任务重连后送达”，完整机制进详情。 /【理由】用户需要预测本次点击的结果，不能把不同入口的行为混成一个承诺。

### E. hub 任务页与任务抽屉

**H11｜建议修**
【现状】任务表列 agent+ID、机器、状态、提交方、UTC 提交时间、操作；筛选有全协议状态、ID/追踪号、机器，更多筛选已折叠（H:1652-1678）。 /【判断】任务辨识/目标/状态为决策必需；提交方/精确时间/追踪为审计回溯；全协议状态常驻为噪音 /【建议】前置人能辨识的任务摘要与行动状态，提交方进详情，保留时间及机器筛选，投递细态折叠为诊断。 /【理由】同一 agent 的十个任务应能直接区分，不能靠打开十个编号来认工作；此条承接技术提案已有任务辨识问题，不再重复视觉方案。

**H12｜可不修**
【现状】当前筛选可导出 JSON，页尾说明保留期；详情可导出单任务（H:1650、1668、1912-1913）。 /【判断】审计回溯 /【建议】折叠导出到更多操作，保留到期提醒与当前筛选范围。 /【理由】导出是可信交付的后备路径，不需要占据每次浏览的主要动作。

**H13｜建议修**
【现状】任务详情含目标/状态、任务号、trace、提交标签、时间、恢复密钥、原始输入、指令、错误、答复、日志、产物、时间线及核对区（H:1882-1913）。 /【判断】指令/错误/答复/产物/核对为决策必需；其余为审计回溯 /【建议】前置当前结论与下一步，折叠身份与原始输入到“诊断信息”，有结果时先交付结果、指令保持预览。 /【理由】用户打开详情应先拿到答案或知道怎样解除异常，而不是先读一串身份字段。

**H14｜建议修**
【现状】失败原因区展示 stderr，另有状态错误提示和折叠诊断日志；日志中又包含 stderr（H:1896、1903-1905；H:294-298）。 /【判断】失败摘要为决策必需；错误码/退出码/原始输出为审计回溯 /【建议】前置一条“发生什么、能做什么”的摘要，原始 stderr、错误码和退出码进详情，取消重复全文。 /【理由】三份失败信息不会让原因更清楚，用户要的是一个可行动的解释。

**H15｜建议修**
【现状】产物列显示路径、精确字节、截断 SHA-256、取回按钮和长机制说明（H:1906-1908、1927-1930）。 /【判断】产物名称/取回/失败反馈为决策必需；摘要与字节数为审计回溯 /【建议】前置文件名、易读大小与取回动作，完整路径/校验值进详情，保留文件可取性提示。 /【理由】校验必须自动执行，展示一段肉眼无法核验的哈希不增加信任。

**H16｜必须修**
【现状】取消后的双端说明均承诺“执行进程已整组终止”（H:1889；N:1812），hub 实际先落 cancelled，再尽力发送取消，离线重连补发（internal/hub/core/cancel.go:13-28、49-54、83-103）。 /【判断】决策必需 /【建议】前置取消请求与执行机确认的区别；无确认依据时显示“已登记取消，执行机停止情况待确认”，不得直接宣布已停。 /【理由】用户可能据此立刻操作同一工作目录，未证实的停止承诺会造成实际冲突。

**H17｜可不修**
【现状】needs_review 显式禁止重提，要求依据、登记有效/失败，并保留原始终态及人工核对记录（H:1932-1950）；时间线列受理、开始、终态、核对（H:283-292）。 /【判断】核对与证据为决策必需；生命周期为审计回溯 /【建议】前置核对结论及下一步，普通成功任务时间线折叠，异常任务保留关键事件。 /【理由】不自动重跑与不改写事实是已有的信任资产，应该削减外围字段而不是削掉证据链。

### F. hub 工作单

**H18｜建议修**
【现状】列表显示目标/ID、状态、步骤进度、尝试数、任期、创建/关闭时间（H:2916-2933）。 /【判断】目标/阻断/步骤进展为决策必需；尝试数/任期/精确日期为审计回溯 /【建议】前置工作目标、阻断步骤与下一步，尝试/任期/关闭时间进详情；工作单作为多步任务关联入口，不必与任务永久同权重。 /【理由】用户关心整项工作能否交付，而不是执行档案有多少行。

**H19｜建议修**
【现状】详情有步骤描述/备注/执行者/依赖/状态、所有尝试表、收集报告、完整事件时间线（H:3029-3070）。 /【判断】当前阻断/依赖/报告为决策必需；历次尝试和事件为审计回溯 /【建议】前置报告（已结束）或阻断步骤（未结束），尝试与完整事件折叠；涉及决策的人工接管事件保留摘要。 /【理由】一次失败后重派十次不应把最后交付淹没在十条历史中。

**H20｜建议修**
【现状】管理动作虽然折叠，但接管要求手填“新任期标识”，续派要求手填机器和 agent，关闭使用“收集/处置关闭”等术语（H:2963-2987）。 /【判断】接管/续派/结束为决策必需；任期字符串为噪音 /【建议】删除手填任期，由系统生成并留审计；前置“接着执行/结束并留报告”，机器和 agent 复用已有目标选择。 /【理由】恢复工作应以工作意图为输入，不应要求用户构造并发控制标识。

### G. hub 群聊

**H21｜建议修**
【现状】群列表显示目标、状态、所有成员徽标、创建时间、消息条数；建群含固定只读的发言上限 20（H:2651-2665、2858-2866）。 /【判断】目标/是否等我决定为决策必需；成员为上下文；条数/固定输入框为噪音 /【建议】删除消息条数与不可编辑预算输入框，成员折叠，前置“需要决策”或“讨论中”；固定上限保留一句说明。 /【理由】发言多不能证明工作有进展，不能修改的字段不该伪装成可配置项。

**H22｜建议修**
【现状】群详情展示目标、成员、主持状态/当前发言者、预算已用/总数、全文消息、关闭群、转任务；FINAL 前缀触发候选展示（H:2674-2716、2734-2740）。 /【判断】候选结论/转正式任务/预算耗尽/当前发言者为决策必需；逐条消息为审计回溯 /【建议】前置待定结论、需人决定及已转任务去向，消息历史折叠或按需展开，普通运行时预算计数弱化。 /【理由】讨论只有形成决定或进入执行才完成产品闭环，结束群聊不等于工作交付。

### H. hub 策略容量、设置与铃铛

**H23｜建议修**
【现状】独立策略页列信箱条数/字节、全局存储、单消息、投递窗口、离线保留、终态/产物保留、执行并发、产物大小、协议版本，页脚承认主要是常量而非运行快照（H:2372-2389）。 /【判断】保留期与限制命中是决策必需；静态协议额度为噪音 /【建议】删除独立导航，将保留期放结果、大小限制放输入/取回现场，其余进帮助详情。 /【理由】没有使用量与处置动作的常量表不能支持容量判断，不要再为它补一套监控仪表盘。

**H24｜建议修**
【现状】设置同时展示当前账户、常驻修改用户名/密码表单、通知、PAT 创建与令牌名称/前缀/创建/最近使用/有效性/撤销（H:2422-2477）。 /【判断】通知可达与访问撤销为决策必需；创建日期/前缀为审计回溯 /【建议】账户修改和令牌创建折叠，前置通知及令牌用途/最近使用/有效性，前缀与创建时间进详情。 /【理由】认领和撤销一份访问权很重要，持续看到一个空密码表单没有日常价值。

**H25｜必须修**
【现状】PAT 名称占位示例含“只读巡检”（H:2473），同页声明令牌权限与登录相同（H:2477）。 /【判断】决策必需 /【建议】删除暗示受限权限的示例，前置“这是管理员权限，名称不限制权限”，不新增本轮之外的角色系统。 /【理由】用途标签不能被误认成权限保证。

**H26｜建议修**

## 四、第一公里：30 秒内是否知道怎么开始

结论：熟悉代码的本人能用；第二个人还需理解两套角色、三种运行形态和若干协议词。无需欢迎页，只需现有总览按条件给出一个下一步。

**F01｜必须修**
【现状】hub 无任务空态去 API，node 首用要求管家/组网，本机自主运行又被叫离线（H:1208；N:799-810、745）。 /【判断】决策必需 /【建议】前置分情况的一步入口：无执行者→登记/连接；有可用执行者无任务→派第一单；已有任务→看进行中；有异常→先处理异常。 /【理由】系统应该用已知状态选择下一步，而不是让用户自己推理产品装配关系。

**F02｜建议修**
【现状】可用能力数不区分当前在线可派，连接注册成功也不验证 CLI 可执行（H:1183、2186；N:813-814、1147）。 /【判断】健康感知 /【建议】前置已知事实“机器已连接、已登记能力、是否已有执行成功记录”，未验证如实标“尚未验证”，提供现有派单入口。 /【理由】不新建健康分数，不把登记成功冒充执行健康，也不自动执行用户未授权的测试任务。

30 秒检验脚本（未来可机械验收，不是本轮实测）：

1. 首次进入空 hub：十秒内指出“尚无执行者”，能找到添加机器；已有可用目标时找到派任务，无需复制 API。
2. 打开已配服务的自治 node：回答“本机可以做事，不需要连 hub”，不把离线当阻塞。
3. 打开有未决任务的任一端：说出谁在执行哪件事、哪些需要自己处理、下一步入口在哪里。
4. 无管家但有普通服务：仍能完成第一单，不经 MCP 配置。
5. 仅写入连接配置但未成功注册：不能回答“已经连上”；页面明确卡点。

### 双端形态对照要求（仅约束未来实施）

| 同类组件 | hub | node | 允许的能力差异 |
|---|---|---|---|
| 工作列表 | 摘要、目标、行动状态、详情 | 同序、同词、同类筛选 | hub 全网；node 本机，不伪造全网视图 |
| 派单表单 | 执行者、描述、权限、提交反馈 | 同构 | node 仅本机；高级参数按真实能力开放 |
| 异常详情 | 原因、证据、处置、下一步 | 同构 | 端点未具备时明确缺口，不虚构可点操作 |
| 结果区 | 答复、产物、取回反馈 | 同构 | 本机文件与中心中继路径不同，动作必须真实 |
| 通知配置 | 送给谁、事件、启停、测试/投递状态 | 同构 | node 无站内铃铛；不能为了整齐复制它 |

实施前对照另一端组件，实施后双端同组件截图验收；shared block 必须同步。这里不修改白名单或现有交互形态。

## 五、回访：让用户放心离开，也能可靠回来

用户明天回来的理由应是“昨天交代的工作有可收取结果，没完成的有明确原因”，而不是检查服务有没有悄悄死。下面三项是通知/事件能力缺口，不是要求扩建消息中心。

**R01｜必须修**
【现状】渠道卡只显示配置/启停，通知重试穷尽仅记日志，不记录可见投递状态（H:2531-2542；N:1299-1317；internal/notify/dispatch.go:169-187）。 /【判断】健康感知 /【建议】新增最小的最近成功/最近失败与失败原因摘要，失败时前置修复入口；每次重试细节进日志，不必建投递分析页。 /【理由】唯一告警通道失效却不告警，用户只能靠每天打开管理台自保。

**R02｜必须修**
【现状】通知只围绕任务终态，站内通知需主动创建渠道、仅内存保存且有容量上限；本机无站内通知（H:2463、2521；internal/notify/inbox.go:3-10、20-21）。 /【判断】健康感知 /【建议】前置“关闭页面后能否收到异常”，无外部通道时明确未覆盖；需要人处理的状态从持久任务/工作单重建，不能依赖铃铛未读。 /【理由】重启或通知淘汰不能让未处理事故从人的待办中消失；不必为此持久化所有普通消息。

**R03｜建议修**
【现状】工作单 blocked/待收集、群预算耗尽/待定版仅在各自页面显示（H:3039-3044、2699、2740），现有任务终态通知不等价于这些工作层事件。 /【判断】决策必需 /【建议】新增“需人工决策”事件的最小提醒，汇入既有通知渠道；只对受影响工作发，不对所有离线/每条消息广播。 /【理由】单个子任务结束并不告诉用户整项工作已卡住，需要人接棒。

**R04｜建议修**
【现状】任务通知标题与飞书文本主要用 task_id、机器/agent、时长、错误码；普通 webhook/站内可含答复摘要，铃铛点击仅已读（H:2612-2620、2634-2636；internal/notify/notify.go:106-133）。 /【判断】决策必需 /【建议】前置工作摘要、事件影响与回到工作入口，成功可简短、失败/拿不准给下一步；没有可用 URL 时给明确导航，不能伪造深链。 /【理由】一条提醒应该让用户少做一次全站搜索，而不是只带回一个编号。

**R05｜建议修**
【现状】已完成任务随保留期清理；node “仅存留痕”不能再看详情；hub 导出与工作单报告能提供部分留档（H:1668、3064、3068；N:1444-1448、1483）。 /【判断】审计回溯 /【建议】前置实际到期风险与保存动作，保留“已删除”事实，删除“已归档”等暗示仍可恢复的错误用语（H:3545）。 /【理由】唯一用户也会隔天回来，承诺的结果若已不存在必须解释去向，不需要为留存新增云盘。

回访待办不等于新增“未读业务状态”：先用现有未核对、进行中、失败、blocked/待收集重建列表；需要“已处理失败/已收取结果”持久标记时再依据真实使用证据决定，不先增加一套阅读状态机。通知已读绝不充当人工核对或结果验收。

## 六、信任三问

### 1. agent 在干嘛？——能看执行记录，不能持续看真实进度

**T01｜建议修**
【现状】普通任务时间线只有受理、开始、终态、核对；运行中答复区仅提示尚未到终态，没有逐步行为流（H:283-292、317-325）。工作单有步骤，群聊有发言者，三者粒度不同。 /【判断】决策必需 /【建议】前置工作意图、执行者、开始时间/已持续多久及已知步骤；无实时行为数据时明说“当前只知道进程执行中”，不要伪造百分比或推测进度。 /【理由】诚实地说明观测边界，比一个持续转动的“运行中”更可信。

当前回答程度：知道交给谁、开始没、结束没；复杂任务可查看步骤。缺的是把这件工作的当前事实放到用户找得到的位置；新建实时日志系统不是本轮必选项。

### 2. 会不会闯祸？——有配置边界，容易被展示成更强保证

**T02｜必须修**
【现状】服务和派单展示 permission_mode 原始标签，开放开关只管其他机器新任务，停止开放不停止在途工作（N:981、1133、1154；H:2186-2192）；SPEC.md:264 明确命令白名单不构成 agent 行为隔离。 /【判断】决策必需 /【建议】前置有效权限的可理解说明、来源及“不确定”兜底，开关明确“停止接受外部新任务”；停止现有任务走独立动作，不以“停止开放”替代。 /【理由】授权标签与关闭准入都不能证明 agent 已被沙箱隔离或已经停止。

**T03｜建议修**
【现状】工作事件同时展示 by 与服务端 principal（H:3070），普通任务提交方直接展示 submitted_by（H:1676、1894）。 /【判断】审计回溯 /【建议】进详情时区分“提交标签”和“经服务端验证的主体”，主视图仅保留需要辨认的来源；缺服务端身份不要推断。 /【理由】把调用方自报名称当作操作人，会使出事后的追责建立在不可信证据上。

当前回答程度：已有本机执行配置、环境白名单、权限说明、外部准入、人工取消等基础；缺口在于授权范围不易理解、取消承诺过强、本机没有可达停止入口。优先修事实表达与控制闭环，不先引入多用户角色、审批中心或“安全评分”。

### 3. 出事能不能发现？——终态可发现，告警失效与过程阻断存在盲区

**T04｜必须修**
【现状】通知失败只进日志、铃铛可清空、工作层待决不在现有终态事件内、node 轮询失败静默（internal/notify/dispatch.go:186；internal/notify/inbox.go:8-10；H:3039-3044；N:645）。 /【判断】健康感知 /【建议】前置四个最低限度事实：数据是否过期、是否有未处理异常、关闭页面后是否可通知、取消是否得到确认；底层重试/心跳/代次仍进日志。 /【理由】这些事实直接决定用户能否离开电脑，不需要再增加一个健康总分。

当前回答程度：对已产生且能成功通知的任务终态回答较好；对没有形成终态的工作阻断、监测链路断开、通知自身失效回答不足。全部在线或零未读都不能推出系统没有异常。

## 八、如果明天只有一个用户且时间减半，界面砍到什么程度还能用

保留 hub 三个日常入口：任务、机器、设置。任务即默认首页，内含异常/进行中/最近结果、派任务按钮和详情；机器只负责找到执行者及装机；设置收纳通知与访问。node 保留任务、服务两个日常入口，连接/管家/诊断收进设置。使用上下文决定默认视图，不新增欢迎页。

**X01｜建议修**
【现状】hub 有总览、机器、任务、派发、工作单、群聊、策略容量、设置八入口（H:971）。 /【判断】噪音（一级入口重复） /【建议】删除独立总览/派发/策略导航，任务内保留派单与异常；工作单从关联任务进入，群聊降为按需工具入口。 /【理由】单人每天管理工作不需要先选择八种对象。

**X02｜建议修**
【现状】node 总览与任务重复最近工作，服务页同时塞运行与配置、通知，连接独立占导航（N:676、793-816、988-990、1401-1442）。 /【判断】噪音（路径重复） /【建议】删除独立总览，任务首页看当前工作；服务页看准入/配置生效，连接与通知进设置。 /【理由】本机的主要价值是执行与控制，已经完成的装机不必每日占入口。

**X03｜建议修**
【现状】默认列表含技术 ID、提交方、任期、尝试数、重连次数、哈希等（H:1218、1673-1677、2923-2931；N:873、1478）。 /【判断】噪音（默认决策层） /【建议】删除默认技术列，只留工作摘要、执行者、状态/异常、时间、下一步；原值留详情与导出。 /【理由】删掉这些列不损失一次正常决策。

**X04｜建议修**
【现状】群聊承担讨论、预算、主持与转任务，独立工作单承担恢复/收集（H:2685-2717、2916-2920）。 /【判断】审计回溯 /【建议】折叠为已有工作关联的高级入口，停止新增群活跃度、讨论趋势和管理报表；已有进行中的群/工作单仍必须可达。 /【理由】时间减半优先保证执行闭环，不能因删导航丢掉未完成工作。

**X05｜必须修**
【现状】现有取消、待办计数、本机核对与通知健康存在 H02/H16/N12/N13/R01 所述缺口。 /【判断】决策必需 /【建议】前置并保留这五条闭环，即使因此暂不优化任何装饰和专家配置。 /【理由】唯一用户的时间更少时，最不能依赖他逐台排查和记住系统没告诉他的事实。

极限版任务详情只保留五段：我让它做什么 → 当前事实与下一步 → 结果与可取文件 → 异常核查/停止 → 折叠证据。权限边界、数据陈旧、未确认停止、未配置通知与保留期限只在影响决策时出现。其他技术事实进入详情、诊断或日志；不删除底层账本，不取消去重，不自动重跑不确定任务，不把“砍界面”做成“砍掉找回证据的能力”。

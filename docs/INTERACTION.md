# SwarmMind 交互设计

> 本文说明当前控制台的页面职责、主要流程和反馈要求。页面名称依据双端 Web 实现；接口与状态契约以 [SPEC](../SPEC.md)为准。新增交互仍需原型与验收，不因写入本文而视为已实现。

## 一、角色与操作边界

| 入口 | 使用者 | 可以管理的范围 |
|---|---|---|
| hub 管理台 | 中心端管理员 | 节点接入、全网任务、人工核对、批量派发、PAT 与通知配置 |
| node 本机控制台 | 当前机器的主人 | 本机能力、开放状态、运行配置、本机任务与 hub 连接 |
| hub 模式 MCP / REST | 持有 PAT 的调用者 | 已开放能力的发现与任务调用，以及工具支持的协作能力 |
| node 模式 MCP | 获得本机编排凭据的调用者 | 当前机器的六项发现与执行工具；要求指定 `prime_agent` |

hub 提供管理与路由服务，任务进程在 node 上执行。node 本机控制台不代理全网能力目录；跨机器任务通过 hub 入口发起。

## 二、主要使用流程

### 配置一项本机能力

在 node「服务 → 能力配置」登记 agent，指定命令和工作目录绝对路径、参数、超时与授权项。保存配置后按界面提示应用并重启，随后确认能力出现在本机列表中。

开放开关表示是否允许网络调用。界面应区分本机保存的意愿、与 hub 的同步状态、网内实际可调用状态。关闭开放不等于取消已经执行的任务；取消与开放管理是不同操作。

### 添加节点

在 hub「机器」页启动添加向导，选择 node_id，生成接入令牌和配置。管理员按提示把该身份与令牌登记到 hub 配置并重启，再在目标机器安装 node 或导入接入配置。节点在线且能力登记成功后，才算完成连接验证。

生成部署包不表示 hub 身份配置已自动更新，也不表示目标机器已经安装成功。

### 提交并跟踪任务

- 全网任务：hub「派发」选择节点与能力、填写输入，提交后到「任务」查看。输入按能力卡呈现：开放参数的能力（`allow_args`）出现命令行参数区，一行一个参数、字面量传递；未开放参数的能力只填任务描述（经 stdin 传递）；声明描述转尾参的能力（`stdin_to_arg`）给出对应提示。
- 本机任务：node「任务」选择本机能力，提交后查看本机任务记录；standalone 模式可调用未向网络开放的本机能力。
- 提交结果未知：保留原输入和幂等键，先查询或重试同一请求；不能直接换新键提交来推断上次没有执行。
- 任务终态：显示执行者、结果、退出信息、已登记产物，以及可执行的下一步。

node「我的任务」依据当前本机执行账本展示任务，包含本机提交与 hub 下发两种来源，并合并仅剩提交记录的历史条目。列表支持 limit/offset 分页，默认 200、上限 1000，界面可加载更早记录。它不等于全网全部任务，也不保证永久审计；node 自动清理尚未接线，保留策略仍待确定。

### 处理不确定结果

`needs_review` 表示执行事实不完整，当前界面显示「等你确认」。说明应明确可能已发生外部副作用，要求检查日志、输出文件和实际目标状态。

人工核对记录在 hub 管理台登记。node 控制台目前提供检查信息与 hub 指引，不提供核对记录写入接口。登记核对不会把协议终态改回运行中，也不会自动重新执行。

## 三、页面职责

### hub 管理台

| 页面 | 内容与主要操作 |
|---|---|
| 总览 | 在线节点、任务状态与异常入口 |
| 机器 | 节点状态、能力信息、添加机器向导 |
| 任务 | 全网任务筛选、详情、产物读取、取消与人工核对 |
| 派发 | 单任务或控制批次提交、按能力卡呈现参数输入语义（SPEC 六.五）、Prime 指定、复合目标与可选派发建议 |
| 工作单 | 独立工作单页：Work 列表、详情、任期接管、续派及报告收集 |
| 群聊 | 群列表、消息、任务关联与结果回流 |
| 策略容量 | 当前限制与保留规则的只读说明 |
| 设置 | 账户、访问令牌与通知渠道 |

### node 本机控制台

| 页面 | 内容与主要操作 |
|---|---|
| 总览 | 本机形态、hub 连接、执行记录摘要与诊断信息 |
| 服务 | 能力配置、开放开关、运行配置、本机 Prime 与适用形态下的通知配置 |
| 任务 | 本机能力派发、本机执行任务清单（含 hub 下发）、来源与任务详情 |
| 连接 | hub 接入、配置预览、保存与断开 |

初始 setup 形态显示连接向导与本机环境入口。页面能力可能随 setup、standalone、networked 形态变化，说明和按钮必须与当前形态对应。

## 四、反馈与状态展示要求

1. 交互开始后应及时显示进行中状态；300ms 是可见反馈目标，不代表网络请求必须在该时间内完成。
2. 提交确认、失败、结果未知和任务终态分别提供下一步，例如查看任务、修正输入、查询原请求或人工核对。
3. 主界面采用简明状态说明；技术状态码、错误码、代次和租约放入详情或诊断区，保证仍可追溯。
4. 无法确认的事实明确标注未知，不用「已失败」代替不确定结果，也不以成功提示替代接入或执行验证。
5. 只读页面说明其限制，不提供没有实际作用的操作按钮。每页主要操作应具有明确视觉层级。
6. 任务详情轮询使用稳定分区和局部更新，保持草稿、焦点、滚动和展开状态；迟到响应不得覆盖新会话数据。
7. 双端共享展示逻辑按 SPEC 六.五一致性契约维护。合理差异须对应端点能力，不能仅为视觉对称而承诺不存在的操作。

现有提示文本可为识别当前界面而原样引用，但文档应解释其准确含义。文案修订涉及运行界面时，需要同时修改实现并验证，不通过改测试期望掩盖差异。

## 五、可用性验收

由未参与界面实现的执行者，在没有逐步口头指导的条件下完成以下操作，并记录完成率、误操作和阻塞点：

1. 登记本机能力并确认网络开放状态。
2. 经 hub 发现远端能力、提交任务并获取结果。
3. 在断线恢复后找到原任务与结果，不重复提交。
4. 检查 `needs_review` 任务并在 hub 登记核对记录。
5. 添加一台机器并确认实际上线，而非仅生成配置。
6. 发起批量任务并识别跳过、成功和失败的目标。

专项用例见 [TESTPLAN-FE](TESTPLAN-FE.md)。本清单是验收要求，不声明这些操作已经在某次版本中通过。

## 六、规划边界

Work 管理台视图已经实现。node 的 Work 视图、群聊消息自动分配、长期统计、精细权限和群聊完整协议仍按专题另行评审。派发建议区域当前使用「本地决策模型」作为固定界面标签，但 D1 实际可能调用外部 GLM 服务；该标签不应解释为模型已经在本机运行。

hub 的 `GET /api/v1/tasks` 当前不提供服务端分页或查询参数筛选；node 本机列表的分页见第二节。MCP `swarmmind_tasks` 的筛选在客户端完成。交互设计不能据旧规划将其描述为已有的服务端能力。

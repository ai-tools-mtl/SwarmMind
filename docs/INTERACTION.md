# SwarmMind INTERACTION — 交互设计与生命周期规格（v1.0，2026-10-20）

> 三方讨论产物（Hana 产品编排 + zcode 交互实现 + codex 架构验收）。
> 上位：PLAN.md 生命周期（P0-P5）。本文回答一个问题：**用户怎么用这个系统，每一步是否「看了就会」。**

## 一、产品角色与职责边界（伦哥定，架构含义）

| | 中心端（hub） | 客户端（node） |
|---|---|---|
| 本质 | 控制面：注册、监管、策略 | 服务面 + 消费面：本机 agent 是服务提供者，本机用户也是消费者 |
| 部署 | 公网云机，管理员登录制 | 每台机器，本机回环 + 本机管理令牌 |
| 是否服务端 | **不是**。不承载用户的服务任务 | **是**。服务端能力由本机 agent 提供 |
| 特殊能力 | 可接入 hub 自有 agent 做控制操作（如全网巡检）——hub 以「控制 node」身份登记，管理员批准，禁止自报提权 | 发现全网能力、派单、取产物（经 node 本地 API 代理，ExecProfile 永不出本机） |

## 二、用户旅程矩阵（产品的主干）

### 客户端控制台（node 本机）——三旅程

| 旅程 | 用户心里的话 | 路径（每步对应真实能力） |
|---|---|---|
| ① 服务提供者 | 「我有 codex，想让别的机器能用」 | Agents 页 → 添加/配置 → **接入开关（exposed）** → 看调用统计（近 24h） |
| ② 消费者 | 「我需要代码审查，谁能做？」 | 能力目录（网内已暴露 agent，搜索筛选）→ 派单表单（自动带对方权限模式/在线/离线排队说明）→ 提交 → 我的任务跟踪 → 结果 + 产物取回 |
| ③ 运维 | 「我的 node 状态如何？」 | 概览（连接/epoch/账本三态/信箱余量/最近同步）→ 诊断信息复制 |

### 中心端控制台（hub admin）——四旅程

| 旅程 | 用户心里的话 | 路径 |
|---|---|---|
| ④ 接入管理 | 「新机器要入网」 | 节点管理 → 生成接入配置（token 单次展示 + 配置片段向导）→ 等 node 上线确认 |
| ⑤ 监管 | 「全网现在什么状况」 | 总览（拓扑/任务流/异常汇总）→ 任务监管（全网筛选/下钻）→ needs_review 队列 |
| ⑥ 控制 | 「让巡检 agent 查一遍所有 node」 | 运维控制页 → 选 hub 自有 agent → 批量目标（自动快照+逐项准入结果）→ 执行 → 汇总报告（部分失败可理解展示） |
| ⑦ 策略 | 「配额/保留期什么规则」 | 只读展示 + 「高危变更走 hub 配置文件」指引 |

## 三、页面树与每页主行动（primary action）

**规则：每页恰好一个视觉最重的按钮；只读页不放假按钮，明说只读本身就是反馈。**

客户端控制台（导航按旅程命名，非数据实体命名）：
- 总览 → 主行动「＋派单」；副行动「处理待核对 (N)」（有积压时升格）
- 派任务 → 主行动「确认并提交」（按钮即状态机：就绪→提交中→已确认[变「查看任务」]/失败[「修正后重试」]/结果未知[「同键重试」]）
- 我的任务 → 无创建类主行动（空态主行动=＋派单；筛选无结果=清除筛选）
- 我的服务 → 主行动「＋添加服务」（V0 实为配置指引+暴露开关，表单编辑不做——V0 不做动态能力下发）
- 运维 → 只读，给「复制诊断信息」

中心端控制台：
- 总览 → 主行动「＋接入节点」
- 节点接入 → 主行动「发新接入配置」
- 任务监管 → 只读（异常看板卡=下钻入口）
- 运维控制 → 主行动「运行巡检」（模板化降低表单成本）
- 策略容量 → 只读

## 四、反馈闭环五条硬规则（「不知道怎么操作」的直接解药）

1. 任何点击 300ms 内有可见反馈
2. 任何终态必须带「下一步」链接（提交成功→查看任务；产物取回→查看全部产物；核对完成→回到待办）
3. 开关类操作回显三态：本机意愿 / 待同步 / 网内生效
4. 不确定态必须锁死并可恢复：结果未知冻结表单+幂等键，给查询/同键重试/放弃三条出路
5. 技术态永远配人话：「已接收 · acknowledged」双语格式；needs_review 详情第一句 =「执行到一半机器重启了，结果不确定——等待本机主人核对，请勿重新提交」

## 五、可用性验收（P3 Gate 的硬证据）

**无提示任务测试**：让未参与设计的人独立完成六个任务，记录完成率/误操作/需要解释之处：
1. 暴露一个本机 agent
2. 发现并派单给远端 agent
3. 断线后找到自己的结果
4. 核对一个 needs_review 任务
5. 审批一个新 node 接入（中心端）
6. 发起一次全网巡检并识别部分异常

关键追问：「停止暴露会停止执行中的任务吗？」「待核对的能直接重跑吗？」——答错的即设计缺陷。

## 七、SPEC 增补清单（按阻塞时机分级）

**P1 开工前（不阻塞 P1 协议/存储开发，但 P1 内完成）**：
1. node 本地能力查询 API（GET /api/v1/agents 本机版）
2. 任务列表 API（GET /api/v1/tasks，筛选+分页——任务中心依赖）
3. 消息类型注册表集中定义

**P3 开工前（控制台实现的前置契约）**：
4. 控制台鉴权契约（访问令牌+会话）
5. 核对记录持久化（POST /tasks/{id}/review）
6. 客户端发现与产物代理接口（node 本地 API 代理授权后的能力目录与产物）
7. 接入申请/批准/签发接口（token 单次展示、绑定 node 身份）；撤销与会话失效
8. 控制操作批次接口（POST /control-operations：目标快照/逐项准入/幂等/恢复/汇总）
9. 调用身份 principal（submitted_by 仅显示标签不用于鉴权）
10. exposed 三层语义（准入/可发现/可调用）与已排队任务处理

**P4 开工前**：
11. GROUP-RFC 待闭合四项（协议补帧/历史缺口/人类身份模型/MVP-DoD 对齐）
12. 签发撤销轮换自动化

**已知限制（文档声明）**：调用统计窗口上限=终态保留 24h；企业内网自托管不自动等于 StartLux 权重非商业豁免；V0 不支持任务取消。

## 八、实现成本（zcode 评估采纳）

合计约 3-4 人周（P3 控制台全量），其中 SPEC 增补约 1 周为关键路径。裁剪顺序（工期紧时）：中心端高级筛选 → 服务表单编辑 → 统计图表 → 引导动画。**不可裁剪**：入网向导、needs_review 核对闭环、每页主行动——这三样正是「不知道怎么操作」的直接病灶。

# Prime 编排设计

> Prime 是已有 agent 承担的任务编排角色，界面显示名为「智行管家」。本文描述角色、权限、编排流程与当前限制；多步执行恢复见 [Work RFC](archive/RFC-work-resume.md)。
> 早期方案中的「统筹载体」与 Prime 指同一角色，配置键 `prime_*`、API 路径和 MCP 工具名保持不变。

## 一、职责

用户提供目标、约束和验收条件；Prime 选择已登记的执行能力，拆分任务，提交执行，读取结果和产物，再生成汇总。任务进程仍由 node 启动，hub 负责记录、调度和结果仲裁。

指定 Prime 不会安装新的 agent、赋予操作系统权限或自动配置所有 MCP 客户端。执行能力、连接配置和凭据必须分别具备。

## 二、全网与本机入口

| 入口 | 指定方式 | 调用凭据 | 编排范围 |
|---|---|---|---|
| hub Prime | hub 管理台指定节点与 agent，状态由 `/api/v1/prime` 管理 | agent 的 hub 模式 MCP 使用 PAT | 经 hub 发现和调用网内已开放能力 |
| node Prime | node 主人通过本机管理面指定，保存 `prime_agent` | node 模式 MCP 使用 `prime_token` | 仅本机六项工具，不提供全网目录、协作群或 Work |

两种指定不是同一份授权。hub 指定某个 agent，不会自动把其 node 模式 MCP 变成全网入口。PAT 当前也不应描述成已具备资源级细粒度权限。

node 主人管理面可为已识别的宿主配置合并 MCP 片段。当前仅探测 agent HOME 下既有的 `.zcode/cli/setting.json`，并要求合法 JSON、可用 MCP 二进制与可写路径；成功返回 `wired:true`，否则返回手动配置片段。此机制不能推广为对任意客户端都可自动配置。

## 三、任务编排流程

1. 明确交付物、验收条件、可用执行者和预算。
2. 查询节点与能力，检查执行范围；缺少能力时向用户说明，不虚构可用工具。
3. 拆分独立任务与依赖关系。依赖通过 `depends_on` 引用上游任务的幂等键；任务执行前由平台准备登记产物。
4. 提交任务并保留 task_id、idem_key、目标节点和能力等定位信息。
5. 等待终态；一次 wait 超时只表示等待结束，不表示任务失败或已经停止。
6. 收集最终答复与真实产物引用，单独列出失败、不确定与未完成部分。
7. 多步骤工作先写入 Work，后续任期先读取执行事实，再决定是否续派；工作结束时按完成或放弃语义收集报告。当前 W3 已加入对应工具与提示词工作单节。

同工作目录的并行任务由现有互斥机制约束；不同工作目录也受 node 并发与 hub 投递窗口限制。Prime 自身的任务数或调用预算属于编排策略，不能直接视作服务端已强制执行的资源限制。

## 四、请求重试与重新执行

| 情况 | 应如何处理 |
|---|---|
| 提交响应丢失，是否接受未知 | 用相同 idem_key 和相同内容重试，取得原 task_id |
| 同键但修改了内容 | 发生冲突；不能将它当作更新原任务的接口 |
| 已明确失败，决定进行新的执行 | 先分析失败原因、权限与副作用，再创建新尝试和新幂等键；Work 下还需绑定原步骤与当前任期 |
| 查询或等待超时 | 继续查询原任务；不要仅因调用超时就重新派发 |
| `needs_review` | 停止依赖该结果的后续执行，提交人工核对，不自动重跑 |
| `cancelled` | 记录取消及可能已发生的执行数据；不自动创建替代任务 |

使用同一键不会重新执行已结束任务。修改任务内容后继续沿用同一键也不会修复该任务，而会触发冲突。这一区别必须保留在提示词与接口说明中。

## 五、依赖与文件交接

平台已有同机和跨机输入挂载，不必把所有上游文件嵌入下游提示词。Prime 应通过依赖声明让 node 将已登记文件复制到 `inputs/<上游task_id>/`，并告知执行者读取位置。

文本摘要可以作为任务输入，但不代替文件完整性校验。源节点不可达、上游材料已清理或校验不符时，应说明具体阻塞原因；不能通过自动重跑上游来假定恢复材料。仓库修改也不会自动变成产物，代码交接需显式生成补丁或其他受支持文件。

## 六、分配建议

| 入口 | 当前实现 | 限制 |
|---|---|---|
| `swarmmind_dispatch_suggest` | hub 内嵌决策服务，从在线且开放的目录候选中推荐；D1 使用 llm-as-jev | 可选建议；失败不阻塞任务提交；概率未证明统计校准 |
| `swarmmind_decide` | 旧 MCP 建议接口，可查询配置的 StartLux 服务或退回 L2 本地规则 | 调用者传入候选，与新服务不是同一接口；未实现 L1 本地模型自动切换 |

用户已明确执行者时无需另行查询建议。新建议服务当前并不自动把群消息转换成任务；群聊联动、本地 provider 和级联策略按 D2/D3 推进。

D1 当前可能向外部 GLM 服务发送任务描述及候选摘要。界面「本地决策模型」是现有固定标签，不能据此推断模型在本机运行。模型自报置信度、归一化概率和特定样本正确率都不等于校准证明。

## 七、群聊和 Work 的分工

2026-10-29 补充的产品目标要求把编写与审查分别绑定到固定原生会话，返工追加到原线程。当前 Work 只保存执行事实，Group 只保存讨论；两者都不等于原生会话。现有 Work 步骤固定且完成后锁定，多轮循环需补充建模，不能直接重派已完成步骤。会话映射、版本绑定、停止规则和接管方案见[持久会话协作方案](VISION-persistent-agent-collaboration.md)，本段不表示运行中的 Prime 已具备这些能力。

- 群聊保存讨论、任务关联与结果消息，可作为用户与 Prime 交流的入口。
- Work 保存步骤、尝试、终态和接管记录，是多步骤续管的正式依据。
- hub 不自动选择新 Prime 或重新执行工作。接管者必须先读 Work，再以当前任期执行允许的写操作。
- 群消息或工具输出可能含不可信文本，应按任务数据处理，不能作为更高优先级授权。

## 八、提示词与实现状态

### 8.1 提示词位置

[deploy/prime/PRIME.md](../deploy/prime/PRIME.md) 保存配置说明与当前提示词资产；hub 实际使用 `internal/hub/web/app.js` 中的 `PRIME_PROMPT`。更新提示词行为需要两处一致修改并测试，单改文档不能视为运行行为已更新。

### 8.2 当前已知差异

运行行为节仍含 `startlux_decide` 名称、失败后修改内容仍同键重派，以及跨机大文件尚不支持的描述；这些与当前接口或平台能力不一致。此前 node 模式可编排全网的安装说明已在文档中纠正。当前正确工具名、调用范围和重试语义以本文、SPEC 与 `tools/list` 为准。

当前提示词已包含 W3 的 Work 建单、绑定、接管与收集节，且有文档资产/运行模板一致性测试；这不消除其余旧段落的语义差异。本轮不修改行为模板或测试断言，部署按 [Prime 配置指南](../deploy/prime/README.md)验证实际范围。以下限制仍需后续同步修正运行模板：旧决策工具名、失败重试指导，以及过时的跨机文件限制。

### 8.3 待验收范围

- Work 完整生命周期、Prime 会话中断后的读取与续管。
- 提示词与实际工具参数一致，且不会因等待超时或结果不确定而重复执行。
- 预算耗尽时保留在途任务定位与部分结果。
- 任务内容、日志和产物中的指令文本不能改变授权范围。
- 全网与本机两种配置分别验证，不能以本机只读查询成功替代跨机派发验收。

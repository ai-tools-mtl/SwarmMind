# RFC：Work 工作单与多步骤执行恢复

> 版本：v2，设计日期 2026-10-25。当前开发分支已包含 W1–W3 实现；W4 有特定版本的隔离双机报告，采证边界另见报告附注。
> 接口与错误契约见 [SPEC 六.五/六.六](../../SPEC.md)，验证见 [W1](TESTPLAN-W1-work.md)、[W2](TESTPLAN-W2-work.md)、[W3](TESTPLAN-W3-work.md)测试计划及 [W4 报告](TESTREPORT-w4-p5.md)。代码实现、历史验收和生产部署分别记录。

## 一、需要解决的问题

Prime 将一个目标拆成多个任务后，任务可由 node 独立完成，但拆分计划、执行尝试与收集进度如果只存在于 Prime 会话中，会随该会话中断而失去统一记录。后续接管者需要从已持久化的事实判断哪些工作完成、哪些仍在执行、哪些需要人工处理。

Work 将这些事实保存在 hub，不自动选择新 Prime，也不自行决定是否重新执行失败或不确定的任务。

## 二、核心设计

### 2.1 实体与保留

实体关系为 **Work → Step → Attempt → Task**。

| 实体 | 记录内容 | 主要约束 |
|---|---|---|
| Work | 目标、当前任期、状态、步骤、尝试与事件 | 计划在创建时确定，无任意编辑接口 |
| Step | 序号、描述、目标节点/能力、前置步骤、执行状态 | `depends_on` 使用步骤序号，区别于普通任务的 idem_key 依赖 |
| Attempt | 所属步骤、任务 ID、派发键、执行结局与去重证据 | 同一请求重试不新增尝试；新的真实执行才新增尝试 |
| Event | 单调序号、UTC 时间、事件类别、自报标签和服务端主体 | 与事实变更同事务提交；仅保留最新 200 条 |

Work 目标状态包含 `planning`、`executing`、`blocked`、`collecting`、`done`、`abandoned`。当前支持建单、派发、阻断与收集关闭。`collecting` 仅保留枚举，没有自动推进写入路径；收集事务直接关闭为 `done` 或 `abandoned`。

任务结束记录仍按既有 24 小时规则清理。Work 尝试记录保存定位与去重证据，不延长任务详情或二进制产物的可获取时间。当前清理策略为：未完成 Work 不自动清理，终态 Work 从关闭起保留 30 天；到期清理同时删除创建指纹映射，之后相同计划可创建新单。事件仍只有滚动窗口，不能据此声称全部历史永久可读。

请求重试使用原 idem_key 与相同内容；换内容或发起新的执行需新尝试。单纯更换任期不应产生新尝试，同键重放也不应触发已结束任务重新执行。

### 2.2 生命周期与事务

1. **创建**：经 `swarmmind_work_create` 提交目标与步骤。hub 按规范化 goal+steps 指纹去重；相同内容重试返回原单，不追加创建事件。最多 64 步，依赖深度和级联上限分别为 4 和 8。
2. **绑定派发**：`swarmmind_submit` 携 `work_ref`、`step_seq`、`prime_term` 三个参数。hub 在同一事务内创建任务、登记尝试并更新步骤；任一后续校验失败整体拒绝，不发布部分变更。`attempt_ref` 由 hub 生成，不由调用者任意指定。
3. **终态回写**：result、cancel、过期等路径在事务内将任务结局回写尝试与步骤。启动恢复扫描补记历史遗漏。`needs_review` 作为不确定结局保留，不能合并为可安全重试的普通失败。
4. **收集与关闭**：`swarmmind_work_collect` 要求无在途步骤或尝试。`outcome=done` 要求步骤全部成功；`outcome=abandoned` 可关闭已失败或不确定的工作，并将尚未派发步骤记为跳过。报告必填，关闭后保留原执行结局。相同任期、报告与终态的请求重放返回 `dup:true`，不同内容返回 `work_closed`。
5. **接管**：先读取 Work，再用 expected_term 与 new_term 请求比较后更新。只有匹配当前任期的操作可取得续派权，重复已成功操作按契约返回同一回执；历史任期标签不得复用。旧任期的新派发被拒，其已发任务的真实结果仍允许按任务协议回流。

接管并发的含义是：基于同一旧任期竞争时，最多一方完成有效任期变更。重复回执不会再次变更任期或生成新尝试，不能把任意重复调用的 HTTP 200 都解释为新的接管成功。

### 2.3 决策归属

hub 记录执行事实、执行准入和任期约束；当前 Prime 或用户决定失败处置、是否进行新尝试及如何汇总。存在服务端允许提交的接口，不等于 agent 获准自动重跑 `needs_review` 任务。

## 三、接口范围

| 能力 | 当前接口 | 状态 |
|---|---|---|
| 创建、列表、详情与事件增量 | `swarmmind_work_create/list/get`，对应 `/api/v1/works` 组 | W1 |
| 原子接管 | `swarmmind_work_takeover`，对应 `POST /api/v1/works/{id}/takeover` | W2 |
| 绑定步骤派发 | `swarmmind_submit` 扩展三参数 | W2 |
| 收集与关闭 | `swarmmind_work_collect` / `POST /api/v1/works/{id}/collect` | W3 已实现 |
| 管理台查看与操作 | hub「工作单」页：列表、详情、接管、续派与收集处置 | W3 已实现；node 不提供 |

上述工具仅在 hub 模式装配，node 模式明确不可用。`work_get` 的 `since_events` 返回序号大于游标的现存事件，`pruned_before_events` 标注已清理区间；不能恢复被裁剪的全部事件。

首版产品入口为 Prime/MCP，管理台不提供手工建单；REST 是工具的传输载体，仍接受持有相应管理凭据的直接调用，不应将「无管理台按钮」描述为额外的角色权限强制。

## 四、范围限制

- 不实现 hub 自动选主、自动续派或后台 Prime 接管守护。
- 不加入通用工作流语言、任意计划插入/回滚或 node 步骤账本。
- 不提供泛化 Work PUT/DELETE；状态由经过校验的生命周期动作推进。
- 不延长产物保留，不保存永久日志或二进制镜像。
- 群聊可展示工作进度，但群消息不承担正式步骤绑定或接管依据。
- Git 自动集成与 agent 签名体系不属于本次 Work 范围。

## 五、分批交付与验收

| 批次 | 交付范围 | 核心验收 |
|---|---|---|
| W1 | 模型、事务、创建幂等、列表/详情、事件与主体 | 响应丢失重试返回同单；旧快照兼容；写失败不发布；事件与事实一致 |
| W2 | 接管、步骤绑定、尝试、终态回写与恢复 | 同旧任期竞争仅一方变更；旧任期续派被拒；快速结果不丢；同键不新增尝试 |
| W3 | 收集/关闭、管理台、Prime 提示词、接口与清理补全 | 部分报告不误关闭；阻断可解释；任务清理后仍有执行摘要；提示词与接口一致 |
| W4 | 真实双机与 Prime/hub 故障验收 | 无额外尝试、丢失绑定或重复收集；断线、权限拒绝与产物取回复验 |

W1–W3 已实现；W4 报告声明通过，但仓内 B/C 最终采证不足以独立复核所述关闭结论，详见报告核对注。本轮不重新进行远程故障测试。每批实施前先定义测试要求，完成后独立执行并记录证据。P5 开发分支的代码存在不表示 P4 观察期已经完成，也不构成合入生产分支的授权。

## 六、已确定的边界决策

1. **入口**：首版由 Prime/MCP 建单；管理台按 W3 范围提供查看及明确列出的操作。
2. **身份**：`by`、`created_by` 和 `prime_term` 是请求提供的标签；`principal` 来自服务端鉴权。二者独立记录，任期名不等于调用者身份。
3. **保留**：Work 不延长 Task 与文件可取时间；未完成单不自动清理，终态单从关闭起保留 30 天。原始事件使用滚动窗口，不承诺永久审计。

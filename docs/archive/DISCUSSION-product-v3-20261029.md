## 收敛结论

- Hub通常不部署agent或管家，外部agent仅为可选MCP调用者；Hub仍能经网页、明确规则与可选jev独立推进。
- 客户端独立拥有本机会话/协作/MCP；两端共享内核，范围不同。
- jev输出经过校验；外部管家有开放计划表达能力，但执行动作统一授权、任期、幂等和版本校验。
- 消息游标不唤醒成员，显式派发续接原生线程；讨论和写审分别有完成策略。
- 管家断线默认暂停，首版显式接管，不自动切换调度者。
- 首版固定空间归属；延后迁移。原生线程复用须交接所有权，不能在两个空间同时写。
- 最小UI与REST/MCP同步交付；Task/Work退到执行详情，可靠性保留。
- FINAL前缀继续登记候选，后续交付检查不能仅靠文本前缀。

## 一、有争议的决策（先说反对）

**1.「内置执行器」边界未定义——必须修。** 若它是有模型、可用工具的多轮 agent，直接违背硬边界 2「Hub 不部署 agent」。必须钉死为：**无模型确定性状态机**，动作集封闭（按绑定线程投递轮次、登记 FINAL 候选、触发预算/停止规则暂停）；需要判断的有限决策（指名下一位执行成员、收敛建议）调 jev，且 **jev 输出是调度器的输入，不是指令**。Hub 无外部管家的「独立推进」＝机械推进到边界（预算耗尽/争议/权限请求）即停请人。内容生产始终在成员原生线程里完成，Hub 只管路由与收敛——这不是能力缺陷，是职责划分，文档要这样写明，否则「内置执行器」会悄悄长成一个藏在 Hub 里的完整 agent。

**2.「每成员游标及原生线程绑定」语义危险——必须修。** 若游标驱动唤醒，就是变相消息扇出，违背 GROUP-RFC 第八节 10-28 修订「消息面不扇出、唤醒只经显式派发」。改为：**游标只是读取位置**（展示与召回用）；线程推进只有两个入口——建群并发派发、调度者/人指名追加轮次。

**3.「本地空间迁到 Hub」应砍掉——必须修。** 真实用法是家里先起本地目标、之后想拉公司 agent 参与，需要的是**注册关联**：空间元数据与线程绑定上 Hub 索引，历史正文与原生线程材料永不搬迁、留在节点。迁史制造断点且无收益；个别要换空间的走既有「摘要交接＋损失边界」语义。注册即显式移交调度负责人（对应初稿接管语义），反向降级回本机空间同样显式。

**4.「日常 UI 放最后」与验收判据自相矛盾——必须修。** 里程碑判据「用户两次进入同一线程」没有最小页面无法按测试循环制度做真实使用验收；且 AGENTS.md 已硬规新 REST 同批交付 MCP 工具。最小线程页应随第二步交付，不是第四步。

## 二、必须修改（补充三条）

- **管家/jev 权限状态边界**：外部管家经 MCP 只能发**有限指令集**（推进一轮/暂停/定版/派发/应答权限请求），指令集⊆内置规则动作集，**落空间账本才生效**；调度状态唯一所有者是账本，管家断线自动回落规则驱动或暂停，事实不丢、不许从管家记忆恢复。jev 全程无指令权。两端同构（对齐硬边界 3）。
- **群讨论与写审循环不得统一成一个通用工作流**，改「一个内核、两个收敛器」：内核只管线程绑定/轮次账本/游标/预算/暂停；**群收敛器**＝FINAL 候选＋Host 定版（开放讨论、多人）；**写审收敛器**＝版本哈希＋必须修清零＋停止规则（机器可判、有界返工）。按空间声明挂载。硬塞通用工作流会把讨论逼进死板轮次、把交付保证稀释成闲聊。另初稿漏了 VISION 5.3 已指出的缺口：Work 步骤建单固定、完成步骤不可重派，写审落 Work 须扩展可重复阶段模型，不能当现成支持。
- **断 Hub「已开始任务对账」须写明依据**：按原生轮次 ID 对账，不可确认即 needs_review、禁盲重发（VISION 5.2 已有）。初稿只写「对账」两字，落不了地。

## 三、可保留

一个工作台两范围；Session/Turn 基础、原生 ID 显式绑定、各目标独立线程不默认 latest；Task 降执行层、砍 Task/Work/Group 并列导航（Work 改为空间详情内执行事实区，不再是用户入口）；每空间唯一调度负责人（补驱动者与接管语义后成立）；暂缓清单与 PRODUCT-DIRECTION 一致。

## 四、可收敛替代方案

**「协作内核＋两收敛器＋驱动者角色」**：内核本机/Hub 同构、唯一状态所有者、确定性推进；收敛器按空间挂载、不互相冒充；驱动者缺省＝规则＋jev，可选＝外部管家经 MCP 发有限指令，显式接管换驱动、禁双驱动。开发顺序改为：① 内核＋适配器（REST＋MCP 同批）→ ② 最小线程页（列表/续聊/轮次状态/权限待办，双端同构）→ ③ 写审收敛器（含 Work 可重复阶段扩展）→ ④ 群 FINAL 收敛器 → ⑤ Hub 注册关联与跨机路由 → ⑥ 管家驱动接口。本地迁 Hub 一项取消，改为注册关联。

## 三个争议点裁定

**1. 管家断线处理：接受 Codex，反对我首轮的「自动回落规则驱动」。** Codex 正确：在途请求未决、旧管家可能复联时，自动切换驱动即双重调度。改为：断线＝任期悬挂，暂停新增派发；在途轮次结果照收落账（结果是事实不是协调动作，落账但不触发下一步，留给接管者判读）；切换驱动仅两条路——显式 CAS 任期接管，或事先授权且可按 fencing epoch 证明旧任期失效的策略；恢复的管家同样须过任期校验并从账本重建状态，不信聊天记忆。这与仓库既有 epoch/fencing 和 Work 接管语义同构，我的原提法反而引入新机制。

**2. 首版固定归属：接受。** 注册关联＋负责人移交本质是分布式状态迁移（账本交接、转移期双写防护），首版引入得不偿失。固定「本机目标本机管、中心目标中心管」，中心可路由到客户端成员线程，历史永不搬迁；跨域走显式新空间。补一条落地要件：本机空间不得添加远程成员，UI 文案须写明「需跨机请建中心空间」，防止用户误期待。

**3. 管家指令集：接受 Codex，撤回我首轮两处。** 我混淆了安全与表意：安全靠「影响执行的动作过同一授权/任期/幂等/版本校验门」，不靠限制管家能说什么；管家可开放提出计划与验收建议，内核仍是唯一执行者。VISION 5.4「不让编排 agent 自动扩大授权」直接判我首轮的「应答权限请求」错——从管家缺省指令集删除，仅人事先显式授权且留审计。

## 剩余必须修问题

无产品边界级分歧，**第二轮边界收敛**。但 RFC 落地须带四件事（非争议，防走样）：

1. 任期策略具体判定：心跳超时时长、epoch 校验步骤、「事先授权」的配置形态；
2. jev 候选校验语义：指名成员存在/获授权/预算内，校验拒绝后回退手选而非静默改选；
3. 管家指令的审计主体由服务端解析（PAT 名等独立字段落账），不采信自报身份——AGENTS.md 既有硬规；
4. 跨域换目标时若本机原生线程仍健康，新中心空间可直接重绑原线程 ID（原生续接优于摘要），仅不可绑定时走摘要交接并记录损失边界。

定稿边界七条与 A–D 阶段（外部 MCP 自 A 主线）我均无异议，与五条硬边界和既有 GROUP-RFC/VISION 契约核对无冲突。
